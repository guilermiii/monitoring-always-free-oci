Visão Geral e Objetivo do ProjetoO projeto consiste em um dashboard de monitoramento local, empacotado em contêiner, dedicado a rastrear em tempo real e de forma projetada o consumo de recursos dentro das cotas do plano Always Free da Oracle Cloud Infrastructure (OCI). O foco central é alertar preventivamente o usuário sobre o risco de cobranças acidentais, identificando capacidades alocadas (recursos provisionados que cobram por existência) e horas acumuladas de uso no ciclo de faturamento mensal.2. Arquitetura da Solução e Stack TecnológicaFrontend: Aplicação SPA desenvolvida em React com estilização via Tailwind CSS, priorizando interface moderna, componentes visuais com ícones e gráficos reativos.Backend: API leve em Python (FastAPI) consumindo a biblioteca oficial OCI Python SDK (oci).Autenticação: O contêiner consome as credenciais já configuradas na máquina hospedeira através da montagem em modo somente leitura do diretório ~/.oci (perfil padrão DEFAULT), eliminando a necessidade de gerenciar senhas ou tokens dentro do código.Empacotamento:Build Único (Single-Container): Multi-stage build empacotando o build estático do frontend compilado diretamente dentro do runtime Python com Uvicorn.Composição com Cache (Multi-Container): Estrutura orquestrada via Docker Compose caso a camada de background worker com Redis seja incorporada.4. Análise de Trade-offs e Decisões de EngenhariaDurante a concepção técnica, foram debatidas abordagens para contornar a lentidão inerente às APIs de faturamento e os riscos de bloqueio por limite de requisições (rate limits):Abordagem A: Cache Nativo em Memória no PythonVantagens: Mantém a experiência de deploy simples através de um único contêiner isolado (docker run). Baixíssimo consumo de memória RAM adicional na máquina host.Desvantagens: A primeira requisição após subir o contêiner sofre a latência de chamada do SDK (cerca de 2 a 5 segundos). Os dados temporários são perdidos se o contêiner for reiniciado.Abordagem B: Desacoplamento com Redis e Background WorkerVantagens: O frontend nunca experimenta lentidão, pois o backend consome o JSON serializado diretamente do Redis em milissegundos. Um processo em segundo plano atualiza as métricas a cada intervalo fixo (ex.: a cada 10 ou 15 minutos), isolando completamente a interface de falhas ou lentidão na API da Oracle (stale-while-revalidate).Desvantagens: Aumenta a complexidade operacional, exigindo Docker Compose com dois serviços e rede interna compartilhada, além de consumir memória contínua para o servidor Redis.Direcionamento Definido: O uso do Redis foi escolhido com foco em desacoplamento e performance de carregamento, permitindo que o monitor opere com atualizações assíncronas e leituras instantâneas no dashboard.5. Cuidados Técnicos e Desafios MapeadosLatência de Faturamento na OCI: A Usage API possui atraso reportado de 4 a 24 horas. Para dados críticos e imediatos (como criação de novos discos), o sistema deve confiar na contagem do inventário (BlockstorageClient) e não em relatórios de cobrança.Normalização de Caminho de Chave (key_file): O arquivo de configuração montado pode conter caminhos absolutos do sistema hospedeiro. O backend Python deve inspecionar e ajustar dinamicamente o caminho da chave privada .pem para o caminho interno montado no contêiner.Permissões de Arquivo: O SDK da OCI rejeita chaves privadas cujo arquivo possua permissões excessivamente abertas no sistema operacional (exigindo permissão restrita equivalente a 600).Varredura Recursiva de Compartimentos: Recursos criados fora do compartimento raiz (root) não aparecem em buscas simples. O backend deve percorrer a árvore de compartimentos para somar volumes espalhados na tenancy.Modo Volátil no Redis: Caso o Redis seja utilizado, a persistência contínua em disco (snapshots RDB e logs AOF) deve ser desativada para evitar I/O desnecessário no disco local da máquina.6.
